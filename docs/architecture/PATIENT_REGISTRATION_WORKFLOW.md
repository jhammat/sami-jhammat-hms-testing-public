
## Purpose

Patient registration creates the patient identity before appointments, services
or encounters are added.

```text
Hospital staff
→ Patient identity
→ Validation
→ Save patient
→ Generate MR number
→ Continue hospital workflow
```

## User Context

This workflow is intended for trained hospital staff.

It is not a public self-registration portal.

## Save-First Principle

The patient record is saved independently before:

- Appointment booking
- Encounter creation
- Consultation
- Service ordering
- Billing
- Laboratory orders
- Radiology orders
- Pharmacy dispensing
- Admission

This avoids creating partial clinical or financial activity for an unsaved
patient.

## Essential Registration Fields

Essential fields include:

- Registration branch
- First name
- Family name
- Gender
- Date of birth or estimated age
- Mobile number

## Additional Fields

The workflow also supports:

- Middle name
- Alternate mobile number
- Email address
- National identity number or passport
- Blood group
- Patient category
- Preferred language
- City
- Address
- Emergency contact
- Referral source
- Administrative notes
- Contact permission

## Smart Defaults

Current defaults include:

- First connected hospital branch
- Islamabad city
- Self-pay patient category
- English language
- Walk-in referral source
- Contact permission enabled

Defaults reduce repetitive typing but remain editable.

## Gender and Age Visibility

Gender and age information receive prominent placement because they are
frequently required during hospital identification and clinical workflows.

When date of birth is unavailable, staff may record estimated age.

## MR Number

After successful validation, WonFlow generates a demonstration medical-record
number:

```text
MR-YYYY-XXXXXX
```

Production MR numbers will be generated by the backend using organization-level
identity rules and concurrency-safe database logic.

## Current Frontend Persistence

During the frontend demonstration stage:

```text
Valid registration
→ Browser local storage
→ Fictional patient result
```

This is not production persistence.

Production registration will use:

```text
Secure API
→ Authorization
→ Duplicate checking
→ Transaction
→ PostgreSQL
→ Audit log
```

## Validation

Frontend validation checks:

- Required branch
- Required patient names
- Required gender
- Date of birth or estimated age
- Estimated-age range
- Mobile-number format
- Alternate-number format
- Emergency-number format
- Email format

Backend validation will remain mandatory in production.

## Duplicate Detection Boundary

The production workflow must check potential duplicates using controlled fields
such as:

- National identity number
- Passport number
- Mobile number
- Name
- Date of birth
- Existing MR number

The frontend-only demonstration does not establish authoritative duplicate
detection.

## Privacy Boundary

Production registration requires:

- Authorized hospital user
- Branch context
- Role permission
- Audit logging
- Data encryption
- Secure sessions
- Consent handling
- Retention policy
- Patient-data access controls

## Safety Rules

1. Registration is performed by hospital staff.
2. Patient identity is saved before service activity.
3. Gender and age remain visible.
4. Date of birth or estimated age is required.
5. Phone numbers are validated.
6. Financial or clinical activity is not created automatically.
7. Frontend validation does not replace backend validation.
8. MR numbers are generated securely by the backend in production.
9. Duplicate detection requires an authoritative database search.
10. Fictional records remain visibly identified.
11. Browser-local persistence is demonstration-only.
12. Production registration requires audit logging and permission enforcement.

## Locked Decisions

1. Patient registration is a Hospital Operations workflow.
2. The registration interface is optimized for staff counters.
3. No public onboarding progress bar is used.
4. The form uses compact operational sections.
5. Gender and age are essential fields.
6. Date of birth may be replaced by estimated age.
7. Smart defaults reduce typing.
8. Patient identity is saved first.
9. MR number appears after save.
10. Appointment and service workflows remain separate.
11. Demonstration records are stored locally.
12. Production persistence will use secure backend services.
